# EP 优化结果与闭环

## 目的
先优化路由与通信组织，保留原 PyTorch 专家、Router softmax/Top-K 和 BF16 运算边界，为 6 选 2 从头训练提供可验证的 EP 路径。

## 执行方案
1. 使用稳定的计数→前缀和→scatter 替换两次 argsort；向量化打包时生成本地专家 ID、置换及回传索引。
2. 输出融合逆置换、路由权重乘法及 Top-1/2 合并，显式保留乘法舍入和输出类型转换，禁止乘加融合。
3. 推理工作区按层、设备、stream 复用并按容量增长，每次调用重新计算 counts 与映射。训练保存的激活和映射单独拥有存储，直到反向结束。
4. Decode 可选固定容量 NCCL 分块，padding 专家 ID=-1，接收端 GPU 计算有效 counts；原专家 GEMM 仍按紧凑有效行数执行，因此仍有一次 counts 主机读取。
5. 专家总数 E、Top-K、Rank 数 R 可配置，要求 E 能被 R 整除、1≤Top-K≤E。2/3 个桶保留快速路径，其他桶数使用运行时分桶；接口限制每个分桶轴为 1～1024，实际模型测试覆盖 R=1/2/3/4、E=4/6/8，不能将接口上限当成全范围性能保证。
6. Top-K>2 先融合单条赋值的加权与逆置换，再用原 PyTorch index_add_ 归约。原生多路浮点归约可能不逐位确定；前向对照和反向公式分别验证。
7. 比较 compact、固定容量 Decode、按 Rank 去重及分块计算。只采纳数值通过且端到端有收益的方案。

具体执行见[指令篇](../commands/08_EP优化.md)，数值和性能见[结果篇](08_EP优化.md)。

## 结果
最终配置验证 716 项通过，全部三个功能算子的 schema、autograd、FakeTensor、AOT 动态检查通过。1/2/3/4 Rank 的真实 NCCL 模型与梯度测试通过。Top-1/2 要求逐元素一致；Top-K>2 保留原归约并验证有界舍入，不宣传逐位一致。原尺寸 768×2432、8 层、6 专家模型再次通过完整输出、人工边界、动态路由和训练梯度复验。

最终通用配置的 memcheck、racecheck、synccheck 各覆盖 647 项，均无报错；racecheck 无竞争警告。最终性能复测 28 次 GPU 占用采样未发现其他任务共用测试双卡。

| 每 Rank 输入 / Top-2 | 原 PyTorch EP / ms | 优化 EP / ms | 延迟降低 |
| --- | ---: | ---: | ---: |
| Decode B1×1 | 12.220 | 9.118 | 25.38% |
| Decode B16×1 | 12.944 | 9.746 | 24.71% |
| Prefill B1×128 | 12.148 | 9.327 | 23.22% |
| Prefill B8×340 | 18.411 | 15.521 | 15.70% |
| Prefill B32×340 | 58.971 | 53.609 | 9.09% |

性能对象为原 4 专家 checkpoint；Top-2 是同权重的路由实验。最终策略为 Prefill compact、Decode 固定容量；训练使用 compact。全模型含 attention、8 层 EP、原专家及末位置 logits；不包含采样和分词，不使用全 EP CUDA Graph。

## 调整闭环
- 初版 FP32 合并因乘加融合出现末位差异：改用显式乘法舍入并设置 --fmad=false，重新对照通过。
- 原始 raw out 接口不适合自动求导：增加功能式 custom_op、FakeTensor 及梯度注册，训练映射和激活不复用活跃存储。
- 4/6 专家、Top-1/2、双 Rank 的限制：补运行时分桶、动态 Rank 循环、通用固定容量，增加多 Rank 整模型测试。
- 多路归约初次要求逐位相同失败：原 PyTorch 重复运行也存在末位变化；保持原 index_add_，用原两次索引链验证打包反向，并将归约波动与梯度公式分开测试。
- 去重减少输入传输，但增加 nonzero、展开和元数据成本；最终同轮 Top-2 全部慢于 compact，保留为实验模式，正式训练不采用。
- 直接把原专家拆成两块计算改变了 BF16 GEMM 输出；6 个测试全部有差异，暂不开展该分块流水方案。
- 通用路径仍有 CPU 动态 splits/有效专家行数读取；动态 EP 编排作为明确 compile 边界，优先编译专家与其余张量计算。

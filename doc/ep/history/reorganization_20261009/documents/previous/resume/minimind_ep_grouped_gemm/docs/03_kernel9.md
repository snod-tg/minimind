# 03 kernel9：动态 M 的 Grouped GEMM

## 目的
原 kernel8 的优化范围是 E=16、总 M=2048、N=K=1024。MiniMind-EP 的本地专家行数随路由变化，实际 gate/up 为 K=768、N=2432，down 为 K=2432、N=768，输入输出为 BF16。本阶段将计算核心扩展到这些真实维度，使 GPU counts 驱动调度，并验证收益能否成立。

## 执行方案
1. 保留 kernel8，在同一源码新增 kernel9，共用 common.h；支持三组固定 N/K、FP16/BF16、E=1～16、动态总 M/专家 M。输入按专家连续打包，FP32 累加。
2. 由 GPU counts 生成行 offsets 和输出 Tile 前缀，计算 kernel 在设备上定位专家。CPU 只用张量 shape 决定 grid 容量；测试同一 Graph 改变 counts 的情况。
3. 扫描 BM=16/32/64、BN=128、BK=32、两/三阶段流水线以及 dense/persistent 调度。针对小 M 的长 K 投影增加 Split-K=4/8，在预分配 FP32 工作区合并后舍入输出。
4. 对照 FP32 GPU matmul 和 CPU double 抽样；覆盖零行、空专家、集中分配、尾块、大 M 和真实投影，随后用三种 Compute Sanitizer 工具检查内存与同步。
5. 对相同输入扫描 CUTLASS 分块、调度和 CTA 数。确定 kernel9 的正常默认调用策略后，同轮交替复测两者；分别报告纯计算和元数据加计算。
6. 将通过验证的实现同步到 my_cuda_kernels，保留原分析，新增动态 M 的分析和图表。PyTorch 注册、完整 MLP 与模型接入在后续阶段验证。

执行主机、完整命令和各轮对应关系见 [执行指令](../commands/03_kernel9.md)，硬件与软件版本见 [测试环境](../测试环境.md)。

## 结果
状态：已完成，2026年10月7日。

- kernel9 支持动态总 M 和专家分配；实测覆盖 M=0～65536、单专家 M 至 32769，以及三组 N/K。接口使用 int32 索引上限，实测范围不能外推为整个 int32 范围已验证。
- 102 组合成输入、108 次真实分组投影，合计 2928 次计算配置验证通过；Graph 内动态 counts 的 168 次验证通过；22 组 sanitizer 检查通过。最终 CLI 的大 M、Split-K 与 kernel8 回归通过。
- M=1 的 down 纯计算由第一版 23.368 μs 降至最终默认路径 5.611 μs；M=1/16 的 down 吞吐分别达到所测 CUTLASS 配置的 189.0%/181.7%。Prefill 四个投影负载为 79.8%～90.0%；M=16 的 gate/up 为 88.2%。
- 以上性能来自单 Rank、预分配、热缓存的算子测量；gate/up 表示一次投影，未融合两次 GEMM。当前没有新 MLP、EP 或完整模型的加速结论。

完整数据、阈值和支持边界见 [结果](../results/03_kernel9.md)。

## 调整闭环
| 问题/证据 | 假设与调整 | 验证结果 | 下一步判断 |
| --- | --- | --- | --- |
| 固定 kernel8 不覆盖 BF16/模型维度 | 参数化计算核心，GPU counts 生成元数据 | 编译、模型投影和动态 counts 通过 | 进入性能筛选 |
| 大 M 的 CPU 抽样索引越界 | 用 int64 整数计算采样位置 | R04/R09 完整验证通过 | 修正测试工具，未把工具错误归为计算错误 |
| 部分 CUTLASS 配置不满足资源条件 | 单独记录排除项并清理 CUDA 错误 | 1620 个有效配置完成扫描，60 个资源不支持项排除 | 以有限扫描中的最优配置为比较对象 |
| 小 M down 只有 6 个有效输出 CTA | 沿 K 分成 4/8 份，增加并行度，FP32 合并 | M=1 down 改善约 4.16 倍，重新通过数值/安全验证 | 小 M 默认启用；限制 M≤64，控制工作区与额外开销 |
| 测试选优不等于正常 API 的选择 | 将有限样本中的规律变为仅依赖 M/N/K 的默认策略 | R14 使用 config=-1 同轮复测 | 不宣称对所有 counts 最优 |
| Prefill 仍落后所测 CUTLASS | 检查编译资源并尝试 NCU full | 无寄存器 spill；计数器权限不足，NCU 未获得数据 | 后续结合完整接入开销判断收益；瓶颈假设待实测 |

阶段 04 将建立正式 PyTorch API，并处理 tensor 属性、设备/stream、权重缓存和工作区生命周期；基准用的 C ABI 适配器不作为已经注册的 PyTorch 接口。

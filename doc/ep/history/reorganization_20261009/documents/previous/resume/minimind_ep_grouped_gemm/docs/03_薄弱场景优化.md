# Decode 优化：阶段03第四轮闭环

## 目的
按2026-10-09确认的范围，仅优化 Decode M=137、counts=[64,73]、(K,N)=(768,2432)的 gate/up 投影，达到所测最优 CUTLASS 吞吐的80%。Prefill 已达到门槛，本轮保留源码和选路。原模型默认 BF16、兼容路径和 KN 权重保存工作流继续保留；手写 CUDA 按 FP32 累加参考验证。

## 执行方案
1. 在4090D GPU4/CPU28顺序执行。构建使用独立输出目录，保留每轮构建对应的源码；正式计时与验证、安全检查分开。
2. 阅读 DeepGEMM 的 `deep_gemm/include/deep_gemm/scheduler/gemm.cuh`：masked 根据 GPU 有效 M 跳过空组，persistent CTA 以固定步长取下一个 Tile；其 SM90 的 TMA/WGMMA 不适用于4090D。本实现继续使用已有 SM89 cp.async/ldmatrix/mma.sync。
3. 用 GPU counts 直接计算各专家有效 Tile 前缀，并统一映射任务；E=2用两次shuffle快速定位，其余 E<=16 用warp前缀和。紧凑网格上界为 `(ceil(M/BM)+min(M,E)-1)*(N/BN)`，无需CPU读取分配和单独元数据kernel；容量上界不等于有效Tile数。
4. 同轮比较 flat、persistent 1 CTA/SM 和 2 CTA/SM；选择满足性能门槛的实测配置，删去实验配置。保留小 M 原 Split-K；最终gate/up M>64默认新配置，M分配不写死。
5. 目标配置使用 BM32/BN64/BK64、4warps、3阶段流水线、寄存器双缓冲；复用common.h已有完整K掩码、跨stage预取和共享内存中转16B写回。persistent每次复用共享内存前做CTA同步。
6. 全配置FP16/BF16与真实投影回归；额外检查M137、E=1/2/4/8/16、空专家、极端分配、Graph内GPU counts变更、非法counts不写输出。检查masked预整理和pack/unpack成本。
7. 默认路径与CUTLASS重新调参后比较全部8个Decode场景；目标独立复测，memcheck/racecheck/synccheck和独立CLI验收。具体命令见[执行指令](../commands/03_薄弱场景优化.md)。

## 结果
调度同轮筛选：flat 8.493μs，1 CTA/SM 11.474μs，2 CTA/SM 8.232μs；CUTLASS 7.099μs。2 CTA/SM候选进入最终默认构建。最终正常选路8.283μs、CUTLASS 7.154μs，达到86.36%；独立复测86.02%，完成80%门槛。完整数值、82项动态分配、23组安全及7项独立CLI均通过；详见[结果](../results/03_薄弱场景优化.md)。

## 调整闭环
- 仅移植完整K流水线时约9.984μs，改善不够；改为有效Tile映射，减少空CTA。
- flat调度达到83.8%的候选门槛后，按DeepGEMM方向比较persistent；1 CTA/SM并行度不足，2 CTA/SM约86.2%，据此收敛。
- 最终保留7个既有配置加1个新配置。Prefill/common.h保持字节一致；不为追求80%改变原BF16默认归约或误差阈值。
- 计数器权限不足的既有NCU结果不能作为本轮bank conflict或stall测量证据。性能归因以调度对照和源码机制为依据。

- 同进程新旧库比较发现`decode_config::cfg`的GNU unique符号合并，旧结构读取新表可能除零。新表使用独立名称`dispatch_configs`；重新构建并重跑，正式结果只采用修复后的库。
